Kanalvælger // Communication channel picker

Professional work for Digitaliseringsstyrelsen

1 / 4
Problem
Digitaliseringsstyrelsen communicates through more than ten channels, and employees had no shared way of deciding which one fits a given message. With the entire population as the audience, the wrong channel means the message doesn’t reach the people it’s meant for.
My role
I designed, built and maintained the tool end to end: the decision-tree logic, the React interface, the build pipeline and the deployment. I ran user workshops and survey tests with employees, and iterated on the content with the communications manager.
Technical decision
I designed the tool so people without development experience could maintain it. The decision tree is kept separate from the React code, and a GitLab CI/CD pipeline builds it into a single self-contained HTML file that is embedded in Umbraco. Updating the tree means editing the content, and the pipeline handles the rest: no hosting to manage and no changes to the CMS core.
Result
In production since February 2026, used by offices across the agency. Builds and deployments are automated with GitLab CI/CD. I documented the setup and handed it over, and it is now maintained by communications staff without developer involvement.
Tech stack
React, Vite, Umbraco, GitLab CI/CD

Refugee Camp Management

University project in collaboration with Netlight and UNHCR

1 / 5
Problem
Camp staff needed one place to see the camp map, handle reception and maintenance requests and follow population statistics, instead of spreadsheets and printed out maps.
My role
Working in a student team, I worked across the stack. I created wireframes and a LO-FI prototype. I built the header and navigation, set up the frontend test suite with Jest and React Testing Library, and added sorting of reception requests by date. I also took the app to production, creating the Azure deployment pipeline, connecting the deployed API to its database, seeding camp data at startup and moving API URLs into environment config.
Technical decision
Every fetch call in the frontend pointed at a hardcoded localhost URL, which broke as soon as the app was deployed. I moved the API base URL into Vite environment files so the same code runs locally and in production, and added a navigation fallback to the Azure Static Web Apps config so refreshing a page no longer returned a 404.
Result
Deployed on Azure, with the React frontend on Static Web Apps and the .NET API on App Service. Frontend and backend tests run automatically in GitHub Actions. It was very well received amongst stakeholders.
Tech stack
React, TypeScript, Vite, Tailwind CSS, Mapbox GL, ECharts, ASP.NET Core (.NET 8), Entity Framework Core, SQLite, Jest, Azure, GitHub Actions

Chirp

University project

1 / 4
Problem
The brief for the Analysis, Design and Software Architecture course: build “Chirp”, a small Twitter-like platform, and evolve it week by week from a command-line program into a deployed web application with accounts, following and a real database.
My role
In a group of five, I focused on the data layer and testing. I moved storage from CSV to SQLite and then to Entity Framework Core with a repository pattern, wrote integration tests, and set up end-to-end tests with Playwright. X9 Traffic Reports

University project

1 / 6
Problem
Drivers have no quick way to warn each other about traffic jams, accidents or speed cameras as they happen. X9 lets them report an incident with a location, a photo and a severity, and see everyone’s reports on a live map.
My role
Solo project in ITU’s Mobile App Development course. I designed and built the whole Android app: sign-in, reporting with photo and location, a live list and map of reports, and a profile screen. I also added two features beyond the requirements: tapping the map to set an incident’s location, which is turned into a street address automatically, and a map that switches to a dark style when the phone’s light sensor detects night driving.
Technical decision
Reports are stored in Firebase’s real-time database, so a new report from one driver shows up on everyone else’s screen instantly, without refreshing. I kept all database code in separate classes behind the screens’ logic, so the interface doesn’t depend on Firebase and could be switched to another backend. Security rules ensure that users can only edit or delete their own reports.
Result
A working app with real-time sync across users, photo upload, GPS location and a live map, built from weekly exercises to the final hand-in.
Tech stack
Kotlin, Android, Jetpack Compose, MVVM, Firebase (Authentication, Realtime Database, Storage), Google Maps, Fused Location Provider

Interactive Map of Denmark

University project

1 / 6
Problem
Our first-year project: turn raw OpenStreetMap data for the whole of Denmark into a desktop map that you can pan, zoom, search and plan routes on, fast enough to feel smooth.
My role
In a group of five, I built the R-tree spatial index and supported nearest-neighbour search and route planning with Dijkstra’s algorithm. I handled OpenStreetMap relations such as lakes and coastlines and built the zoom levels and map layers, the scale bar, night mode and much of the toolbar.
Technical decision
To keep panning smooth with the whole country loaded, I implemented an R-tree that groups map elements by their bounding boxes. Each redraw only asks for the elements inside the visible area, and the zoom level decides which layers are drawn, so small streets are skipped when you look at all of Denmark.
Result
A working map of Denmark with address search and autocomplete, car and walking routes, night mode, and support for loading custom .osm files.
Tech stack
Java, JavaFX, Gradle, JUnit, OpenStreetMap

Markerless Pose Estimation

University project

1 / 4
Problem
People recovering from knee injuries do most of their exercises at home, with no one to tell them if they’re doing them right. AI models that track body movement from an ordinary camera could fill that gap, but nobody knew how accurate they are on rehabilitation exercises, many of which are done sitting or lying down.
My role
Bachelor project at ITU with Lisa Claudi Hauge, supervised by Stella Grasshof. I built the testing setup in Python: it ran three movement-tracking models on video of eight knee exercises, filmed from five angles, measured the knee angle each model reported, and compared it with precise lab measurements of the same movements.
Technical decision
Some camera angles make a knee angle hard to read, no matter how good the model is. So I also calculated how accurate a perfect model could be from each angle. That way, we could tell whether a poor result came from the model or from where the camera was placed.
Result
No model was accurate enough in every situation, and some camera angles couldn’t reach the clinical target at all. The most accurate model was too slow to run live. The fast one, MediaPipe, came close to the accuracy of a physiotherapist measuring by hand, as long as the camera faced the patient at about 1 m height. In short: a phone placed in front of you, with the right model, could already give useful feedback on seated exercises.
Tech stack
Python, MediaPipe, MMPose, OpenPose, MotionBERT, NumPy, pandas, OpenCV

How this site was built

I built this site with Claude Code, an AI coding assistant that works in the terminal. My workflow:

  1. I wrote a brief with the tech constraints, accessibility and performance requirements, and the design direction.
  2. Claude Code proposed a plan – file structure, design tokens and page sections – which I reviewed and approved before any code was written.
  3. It generated plain semantic HTML and CSS with no framework or build step, and checked the colour contrast ratios against WCAG AA.
  4. I reviewed the output, edited it, wrote all the content, and tested it with Lighthouse and keyboard navigation.
